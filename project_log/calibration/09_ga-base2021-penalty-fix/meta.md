## 手法

08_ga-base2021-E10000-time と同じ入力（基準年2021・中心地32・所要時間で集約）と同じ fitness 関数
`calibration_fitness_housing_survey` で、次の2点だけ変えて GA を回し直す（ユーザー決定 2026-11-18）。

### 1. ペナルティ項の修正（メインスクリプト `calibration_fitness_housing_survey` 内）

- **経緯**：01（5変数のみのGA、k_i=0.1固定）で作られた式が、02で852次元（5変数＋k_i 847）にしたときそのまま使われた。
  `x0` は長さ5なので R のリサイクルで k_i 部分にも `0.3, 0.2, 0.6, 0.1, 2.0` が順に当たり、
  k_i はゾーンの並び順だけで決まる値に引っ張られていた。ペナルティが fitness の約97%を占めていた（08 meta.md）。
- **変更前**（先生の元コードから02以降そのまま）：

  ```r
  penalty <- lambda * sum(((x - x0) / x0) ^ 2)
  ```

- **変更後**：

  ```r
  penalty <- lambda * sum(((x[1:5] - x0) / x0) ^ 2) +
    lambda * mean(((x[-(1:5)] - 0.1) / 0.1) ^ 2)
  ```

  $$P = 0.05 \sum_{n=1}^{5} \left(\frac{x_n - x^0_n}{x^0_n}\right)^2 + 0.05 \cdot \frac{1}{847} \sum_{i=1}^{847} \left(\frac{k_i - 0.1}{0.1}\right)^2$$

  - 5変数部分は01の本来の意図どおり（x0 = 0.3, 0.2, 0.6, 0.1, 2.0、λ = 0.05）。
  - k_i 部分は一律 0.1（01で k_i を固定していた値）と比べる。ゾーン数で平均するので、k_i の罰はデータ誤差（約0.5）より小さい大きさ（07の解で約0.06）になる。
  - データ誤差の項（f_hh + 0.5 f_rent + 0.3 f_ar）は変更なし。
- この変更は07の設定（orig17_2014）で GA を回すときにも効く（07の結果自体は旧ペナルティで較正したもの）。

### 2. 初期集団に既存の解を入れる（`ga()` の `suggestions`）

08 は初期集団が全て範囲内のランダム（`set.seed(1)`）で、x0 の水準にも届かなかった。今回は次の3つを初期集団（50個）に入れ、残り47個はランダム。

| 名前 | 中身 |
|---|---|
| sol07 | 07の解（5変数＋k_i） |
| par08_ki07 | 08の5変数＋07のk_i |
| x0_ki01 | x0＋k_i一律0.1（01と同じ考え方の出発点） |

### メインスクリプトの変更（すべて `261118` のコメント付き）

- ペナルティの式（上記）。
- `getOption("luti_calib_trial")` で保存先の試行フォルダを上書きできるようにした（指定しなければ従来どおり）。
- `getOption("luti_ga_maxiter")` で世代数を上書きできるようにした（指定しなければ100）。
- `ga()` に `suggestions = getOption("luti_ga_suggestions")` を追加（指定しなければ NULL＝従来どおり）。
- 計算時間の対策（下の「計算時間の調査」）：
  - GA内の道路配分 `assign_traffic()` に `aon_method = "d"` を追加（既定 `"bi"`）。
  - `registerDoParallel(cl)` を追加（GA後に `registerDoSEQ()`）。元コードでは `# registerDoParallel(cl)` とコメントアウトされていた。
  - `ga()` に渡す fitness を `function(x) calibration_fitness_housing_survey(x)` で包む。

## 計算時間の調査（2026-11-18）

調査用スクリプトは scratchpad（一時）。数値は 08の設定（中心地32）・このMac（10コア）。

1. **GAは並列になっていなかった**：`makeCluster()` で作った9ワーカーは、GA中にCPUをほぼ使っていなかった（2時間で合計0.5秒）。
   GAパッケージは cluster を渡されても foreach の並列先として登録しないため、`registerDoParallel(cl)` がないと
   `%dopar%` は逐次実行になる。元コードの時点で `# registerDoParallel(cl)` とコメントアウトされており、01・02・07・08 も（コードどおりなら）逐次。
2. **1回の fitness 評価の内訳**：時間の約98%が道路配分 `assign_traffic()`（LUTIループ4〜5回×1回）。nleqslv は1秒未満。

   | 設定 | 1回の配分 | 1回の評価（07の解） |
   |---|---|---|
   | 中心地17（07） | 約3.2秒 | 13.2秒 |
   | 中心地32（08） | 約6.2秒 | 25.5秒 |

   配分の最短経路探索の既定（`aon_method = "bi"`）は OD ペアごとの双方向探索なので、OD数（847×中心地数）にほぼ比例する。中心地を17→32にすると約2倍。
3. **`aon_method = "d"`（出発地ごとの一対多ダイクストラ）**：一様なODで配分した結果はリンク交通量・コストとも `"bi"` と完全一致（差0）、時間は 36.2秒→0.6秒。
   fitness 18個（07の解、08の最良、x0、ランダム15）で比較すると 17個は小数6桁まで一致、時間は 639秒→19秒。
   違った1個（ランダム候補、−4.34 vs −200）は配分の反復数も同じで、浮動小数点レベルの差が積み重なり、4回目のLUTIループの nleqslv が収束判定ぎりぎりで失敗（termcd 4）したもの。
   （`aon_method = "nba"` は結果が大きく違うので使わない。）
4. **並列化**：`"bi"` のままでは9ワーカーにしても 9評価 241秒→219秒（ほぼ変わらない。`"bi"` 自体が内部で10スレッド使うため）。
   `"d"` にすると 18評価 19秒（逐次）→6.4秒（9ワーカー）。
5. **並列にしたとき全候補が −200 になった問題**：ワーカー内で `makegraph(beta = beta)` の `beta` が数値（2.89）ではなく base の関数 `beta()` になり
   「attempt to replicate an object of type 'closure'」で失敗していた。GA開始前はワーカーの `beta` は数値だった。
   fitness を `function(x) calibration_fitness_housing_survey(x)` で包むと正常（2世代テストで Best −0.7594 を再現）。
   原因は foreach が ga() の中から変数を探して送る際に、`beta` を base の関数として見つけて上書きしたためと考えられる（`alpha` は base に同名がないので無事）。未検証の推定。
6. **結果**：1世代 約43分（逐次・"bi"）→ 約28秒（並列・"d"）。100世代で約50分の見込み。
